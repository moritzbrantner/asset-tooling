# Generation-to-processing handoff

Generation and processing are separate provenance stages joined by content identity.

A generated artifact is accepted for processing only when its bytes still match the SHA-256 recorded by its generation receipt and that receipt still matches the current asset specification. `asset-tooling` then emits a processing handoff manifest with:

- `input.sha256` — exactly the generation receipt's `output.sha256`;
- `input.mediaType` — the explicit media type expected by the processor;
- lineage to the generation receipt by portable path and SHA-256.

The `input` object intentionally has exactly the same shape as the `artifact` used by processing receipt v2 (`sha256` + `mediaType`). Domain processor adapters can therefore place it directly into a processing receipt without understanding which generator produced the source bytes.

This preserves the ownership boundary:

- Stable Diffusion, TripoSR, or procedural generators own generation algorithms;
- mesh/animation/image processors own processing algorithms;
- `asset-tooling` owns the content-addressed evidence connecting the stages.

The lineage object is supplemental evidence rather than a field inserted into processing receipt v1/v2, because those published receipt schemas remain immutable. The processing receipt's input hash is the canonical join key. A future processing receipt version may make upstream-receipt lineage first-class without rewriting v1/v2.

The handoff does not rerun an expensive model. It validates the accepted generated bytes against the existing generation receipt before processing begins. Full generation replay remains the separate `verify` operation.
